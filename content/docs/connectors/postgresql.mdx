Use PostgreSQL as a current tapstate source for an initial full load and
ongoing change data capture (CDC). The documented preview path uses
PostgreSQL logical replication with `pgoutput` and writes the resulting
operational state to MongoDB.

PostgreSQL is a source in the current preview. This page does not make it a
published tapstate target.

## Before you begin

### Connector availability

The PostgreSQL connector is registered automatically by the Quickstart script. On standalone or fresh server container deployments, the connector catalog starts empty. Confirm that PostgreSQL is registered before authoring connections:

```text
connectors
register postgres
```

See [When registration is required](/docs/guides/register-connectors#when-registration-is-required).

### Prepare a source database

Choose the outcome you need. Each tab is a complete preparation path; you do not need to combine steps from both tabs. In tapstate, `snapshot` copies the rows that exist when the run starts, while `cdc` performs that initial copy and then follows PostgreSQL changes from WAL.

<SourceModeTabs label="Choose the PostgreSQL source read mode">
<SourceModeTab value="snapshot" label="Full load (Snapshot)" description="Copy existing rows once">

Use **Full load** (`Snapshot`) when you need a bounded copy of the selected tables. It does not require logical WAL, a replication slot, or a decoding plugin.

<PreparationSteps>
<PreparationStep title="Create a dedicated reader">

```sql
CREATE USER tapstate WITH PASSWORD 'replace-with-a-secret';
```

</PreparationStep>
<PreparationStep title="Grant access to the selected schemas and tables">

```sql
\c database_name
GRANT CONNECT ON DATABASE database_name TO tapstate;
GRANT USAGE ON SCHEMA schema_name TO tapstate;
GRANT SELECT ON ALL TABLES IN SCHEMA schema_name TO tapstate;
```

If newly created tables should be discoverable without another grant, set default privileges for the role that creates those tables:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE table_owner IN SCHEMA schema_name
GRANT SELECT ON TABLES TO tapstate;
```

Run the default-privileges statement as the role that creates future tables, or name that role with `FOR ROLE` as shown.

</PreparationStep>
</PreparationSteps>

<SourceModeTab value="snapshot-cdc" label="Full load + CDC" description="Copy existing rows, then follow WAL changes">

Use this preparation path when the destination must begin with existing rows,
then stay current as PostgreSQL receives inserts, updates, and deletes.

<PreparationSteps>
<PreparationStep title="Create a dedicated reader with table and replication access">

```sql
CREATE USER tapstate WITH PASSWORD 'replace-with-a-secret';

\c database_name
GRANT CONNECT ON DATABASE database_name TO tapstate;
GRANT USAGE ON SCHEMA schema_name TO tapstate;
GRANT SELECT ON ALL TABLES IN SCHEMA schema_name TO tapstate;
ALTER USER tapstate REPLICATION;
```

If future tables should be discovered automatically, grant default table privileges for the role that creates them:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE table_owner IN SCHEMA schema_name
GRANT SELECT ON TABLES TO tapstate;
```

</PreparationStep>
<PreparationStep title="Use the documented pgoutput path">

The current preview path uses [`pgoutput`](https://www.postgresql.org/docs/current/protocol-logical-replication.html), PostgreSQL's built-in logical replication output plugin. It does not require a server plugin installation.

The connector catalog can expose additional connector-owned values, but this guide does not treat them as equivalent runtime paths. Use `pgoutput` unless a later tapstate release documents another path.

</PreparationStep>
<PreparationStep title="Configure logical WAL capacity">

Configure enough slots and WAL senders for the planned concurrent tasks:

```ini
# postgresql.conf
wal_level = logical
max_replication_slots = 10
max_wal_senders = 10
```

Allow the replication account in `pg_hba.conf`, using an address range and authentication method that match your security policy:

```text
host  replication  tapstate  10.0.0.0/24  scram-sha-256
```

Restart PostgreSQL during an approved maintenance window when the changed server parameters require it. The values above are examples, not tapstate defaults.

</PreparationStep>
<PreparationStep title="Make update and delete keys available">

For a PostgreSQL table embedded by `nest`, set the full previous row so an
update or delete can be placed in the correct assembled document:

```sql
ALTER TABLE schema_name.table_name REPLICA IDENTITY FULL;
```

`REPLICA IDENTITY FULL` increases WAL volume. Evaluate it on representative
tables before enabling CDC in production-like environments.

</PreparationStep>
</PreparationSteps>

## Create a connection

tapstate stores a PostgreSQL source connection as a `.tap.yml` file in the
workspace.

### Source connection

The example below creates a CDC-capable source connection. The connection's
`mode` controls its read capability.

```bash
tapstate new --non-interactive \
  --kind source \
  --connector postgres \
  --id orders_postgres \
  --mode cdc \
  --set host=postgres.internal \
  --set port=5432 \
  --set database=orders \
  --set schema=public \
  --set user='${POSTGRES_READER_USER}' \
  --set password='${POSTGRES_READER_PASSWORD}' \
  --workdir tapstate-work
```

For a full-load-only source, change `--mode cdc` to `--mode snapshot`. The
generated connection uses the same PostgreSQL fields; only the read mode differs.

```yaml title="tapstate-work/source/orders_postgres.tap.yml"
version: tapstate/v1
kind: source
id: orders_postgres
connector: postgres
config:
  deploymentMode: standalone
  host: postgres.internal
  port: 5432
  database: orders
  schema: public
  user: ${POSTGRES_READER_USER}
  password: ${POSTGRES_READER_PASSWORD}
  logPluginName: pgoutput
mode: cdc
tables:
  - orders
```

Use `mode: cdc` only after completing the WAL, plugin, publication, and
replication preparation. The mode does not by itself prove that those database
prerequisites are ready.

## Validate the configuration

```bash
tapstate validate --workdir tapstate-work
```

<ValidationStatusGuide />

Validation does not resolve the host, credentials, or a PostgreSQL server. A
syntactically valid resource that uses `postgres.invalid` can therefore pass
validation. Register the official artifact and run a server-side connection test
before relying on the configuration.

A successful connection test does not prove that CDC can start. It can confirm
network access and credentials while logical replication, a replication slot, a
publication, or replica identity is still missing. Run a small snapshot and
then an insert, update, and delete in a staging database.

Run a staging check that:

1. discovers a selected table;
2. completes a small snapshot;
3. observes an insert, update, and delete through CDC;
4. stops with state retained, starts again, and verifies that later changes
   reach the target. Recovery uses persisted progress and can replay
   unconfirmed changes.

Use these read-only checks while diagnosing the source:

```sql
SHOW wal_level;
SHOW max_replication_slots;
SHOW max_wal_senders;

SELECT slot_name, plugin, slot_type, active, restart_lsn
FROM pg_replication_slots;
```

## Replication slots and recovery

The documented `pgoutput` CDC path uses a logical replication slot. PostgreSQL
retains WAL until the slot confirms progress. With shared capture, tapstate
confirms changes after writing them to its durable change log; each pipeline
then confirms its own target writes. With direct capture (`srs: false` in the
pipeline source), confirmation follows that pipeline's target writes.

| Action or read mode | Slot and recovery behavior |
|---|---|
| Shared capture is reading | Compatible pipelines use one shared slot. A slow consumer catches up from tapstate's log after PostgreSQL releases confirmed WAL. |
| Pause a shared consumer | Capture continues, even if this is the only paused consumer. Retained changes use metadata-store space. |
| Stop with state retained | Other active consumers can keep shared capture moving. Stopping the last reader stops capture and retains the slot, which can accumulate WAL. |
| Pause or retain a direct reader | Its slot cannot advance beyond target-confirmed progress and can retain WAL. |
| Clear state or rerun | With connector cleanup enabled, tapstate attempts to release the slot when no other consumer depends on it. A direct reader releases its own slot. |
| Delete the pipeline | Deletion does not release the slot. If retiring a pipeline, clear its state before deleting it and inspect cleanup results. |
| `snapshot_only` | The bounded read does not create a CDC replication slot. An older leftover slot is not removed automatically. |

Cleanup can fail or time out while state clearing still completes. Check
`connector.release-failed` warnings and the named slot before considering the
source clean. Custom slots and connectors with automatic cleanup disabled
need separate ownership and cleanup review.

Monitor retained WAL while a pipeline is paused, stopped, or unable to write:

```sql
SELECT slot_name, active, active_pid, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots
WHERE slot_type = 'logical';
```

A `replication slot ... is active for PID ...` error means a connection already
owns the slot. Check `active_pid` and the owning capture. Stop the affected
pipeline with its state retained and wait for the stop to complete before
retrying. If the error persists, preserve the metadata, operator state, and
connector logs for investigation.

Do not drop a slot solely because `active` is false. Check every pipeline and
retained recovery dependency, including those on other servers. Older
releases can leave additional slots behind; remove only confirmed unused
slots using your database administration procedure.

Once PostgreSQL confirms a position, writing an earlier checkpoint into
tapstate does not make PostgreSQL replay WAL already released. Likewise, do
not restore old tapstate metadata while readers are active: newer changes
may exist only in the durable shared log. If retained history is missing or
unsafe, tapstate refuses recovery rather than skipping it. See
[Resume or rerun](/docs/concepts/capture-modes#resume-or-rerun) and
[Upgrade to v0.7](/docs/guides/upgrade-to-v0-7).

## Limitations

- Replication slots retain WAL until consumers advance. Monitor `pg_replication_slots` and disk use, and remove a slot only after confirming that no task still depends on it.
- Tables without a suitable replica identity can produce incomplete keys for updates and deletes. `REPLICA IDENTITY FULL` increases WAL volume and should be evaluated on busy tables.
- Capturing changes from partitioned parent tables requires PostgreSQL 13+ with `pgoutput`.
- The current preview does not make a DDL-capture compatibility promise.
- PostgreSQL string types cannot store the zero byte (`\0`); normalize it before writing if it can appear in source data.
- A replication slot can be blocked by long-running database work. Investigate materialized-view refreshes and other sessions if slot creation stalls.
- Do not drop an inactive slot merely because it is inactive; a stopped pipeline may still depend on its position. Remove it only after the owning pipeline has been retired or reset.
- Configure server-side encryption as required and use the TLS connection options available in your tapstate environment.

## Reference

### Connection settings

The documented current path uses the fields below. The local demo relies on
the connector's default `pgoutput` behavior and does not pre-create a slot or
publication. For another deployment, verify that behavior with a staged table
and its intended database account.

| Field | Required | Default | Use |
|---|---:|---|---|
| `deploymentMode` | No | `standalone` | Standalone addressing for the documented path. |
| `host` | Yes | — | PostgreSQL host for standalone mode. |
| `port` | Yes | `5432` | PostgreSQL port for standalone mode. |
| `database` | Yes | — | Database name. |
| `schema` | Yes | — | Schema to discover. |
| `user` | No | — | Database account. |
| `password` | No | — | Database password or secret reference. |
| `logPluginName` | No | `pgoutput` | Incremental method for the documented logical-replication path. |
| `timezone` | No | Empty | Session timezone used for temporal conversion. |
| `allowReplication` | No | `true` | Whether the connection may use PostgreSQL replication. |

### Additional catalog fields

The catalog recognizes the fields below, including decoder and publication
settings inherited from the underlying connector. They are not required by the
documented `pgoutput` path and are not used by the Quickstart. Do not use them
to infer another published PostgreSQL deployment mode.

| Field | Use |
|---|---|
| `partPublication` | Per-table or partial publication setting. |
| `globalPublicationName` | Publication name for the global-publication setting. |
| `extParams` | Additional connection parameters accepted by the connector. |
| `masterSlaveAddress` | Host and port list for a primary/standby deployment. |
| `pgtoHost` | Helper host for a physical-WAL path. |
| `pgtoPort` | Helper port for a physical-WAL path. |
| `defaultWalLogSize` | Connector WAL-size monitor threshold. |
| `checkCdcSlave` | Whether the connector checks CDC standby state; defaults to `false`. |
| `walArchiveDir` | Optional WAL archive directory; no default. |
| `walArchiveRestoreCommand` | Optional WAL archive restore command; no default. |
| `walTdeKey` | EDB transparent-data-encryption key file used by connector-owned WAL handling. |
| `walTdeKeyPassword` | Secret password for the EDB TDE key file. |
| `walTdeKeyWrapAlgorithm` | TDE key wrapping algorithm: `auto`, `aes-256-cbc`, or `aes-128-cbc`; defaults to `auto`. |

### Database-side data reference

This table summarizes PostgreSQL data behavior for the connector. Test uncommon
extension types with representative data before migration.

| Family | Database-side baseline |
|---|---|
| Text | `character`, `character varying`, `text` |
| Numeric | `smallint`, `integer`, `bigint`, `numeric`, `real`, `double precision` |
| Binary and bit | `bytea`, `bit`, `bit varying` |
| Date and time | `date`, `time`, `timestamp`, `timestamptz`, `interval` |
| Spatial and network | `geometry`, `point`, `polygon`, `circle`, `path`, `box`, `line`, `lseg`, `inet`, `cidr`, `macaddr` |
| Structured and other | `uuid`, `xml`, `json`, `jsonb`, arrays, OID and reg* identifier types, `tsvector`, `tsquery` |

Verify uncommon extension types with representative data before relying on the
current preview path.
