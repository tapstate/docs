## Why operational data becomes difficult

Keeping operational data fresh usually means assembling and operating separate CDC, broker, stream-processing, and serving systems:

<DataPathComparison />

Each tool can be the right choice on its own. The operational cost comes from making the tools behave as one system: coordinating offsets, retries, schemas, serialization, upgrades, and observability across every boundary.

Composable streaming stacks remain the right choice when a workload requires a
highly customized event topology. Tapstate's target model focuses on teams whose
main requirement is to keep operational state current through one deployable
data path. See [Tapstate vs. a streaming stack](/docs/overview/vs-streaming-stack)
for the tradeoffs.

## How tapstate works

Capture, Transform, and Serve are three responsibilities in the same operational data path. They let you move from source changes to application-ready state without operating a separate product at every stage.

### Capture — load existing data, then follow changes

Capture loads an initial data set and, when the connector supports it, follows committed changes from database logs or later updates from streams, APIs, and files. Each connector guide describes the available capture modes and the preparation required by the source system.

### Transform — shape data incrementally as it moves

The current preview filters, maps, runs scripted transforms, merges streams,
and uses `nest` to maintain documents assembled from related tables. `join`
remains part of the declared model but is refused by the current runtime.

### Serve — deliver current state

The current release includes `serve.sync` writes to a target connector. The v1
declaration model also contains `serve.query` and `serve.push`, but the current
preview does not execute them. The CLI, REST API, and MCP provide bounded
inspection instead of a stable application-facing data API.

## Current preview boundary

The current preview is a single-node, in-memory runtime. Its Quickstart
captures MySQL orders and PostgreSQL shipments, assembles one document, and
keeps it current with an initial snapshot followed by CDC.
A server restart replays from the source instead of resuming a persisted
offset. See [Architecture](/docs/overview/architecture) for the current and
target boundaries.

## When to use tapstate

Use tapstate when applications, APIs, automation, or AI agents depend on operational data that loses value when it becomes stale. Common examples include inventory availability, logistics tracking, fraud and risk signals, cross-system customer or account views, and AI agents that need current system-of-record data. See [Use cases](/docs/overview/use-cases) for detailed patterns.

## How to use these docs

The documentation follows the same path you use to build a data pipeline:

- **Prepare the current path.** Use the [connector directory](/docs/connectors) to prepare MySQL and PostgreSQL capture with MongoDB materialization, and to distinguish current connectors from roadmap references.
- **Run the shortest path.** Use the [Quickstart](/docs/overview/quickstart) with sample MySQL, PostgreSQL, and MongoDB data in Docker.
- **Explore the data model.** Change both sources in the [order-state demo](/docs/overview/order-state-demo) and watch one assembled document stay current.
- **Author a workspace.** Use the [offline walkthrough](/docs/overview/create-workspace) to create and validate `.tap.yml` resources.
- **Look up exact syntax.** Use the [reference](/docs/reference/dsl-grammar) for resource fields and examples.
- **Work with an AI assistant.** Use [`llms.txt`](/llms.txt) or the page-level Markdown view to provide the same canonical content to an assistant.
