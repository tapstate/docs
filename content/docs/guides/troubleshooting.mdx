Start by identifying which layer produced the failure. A resource-file error, a connection failure, and incorrect destination data require different evidence and different fixes.

## Read the command result

tapstate commands use these exit codes:

| Code | Meaning |
|---:|---|
| `0` | Success |
| `1` | A coded domain diagnostic or refused operation |
| `2` | Invalid command usage |
| `3` | Unavailable in this context, not connected, or not implemented |

Use `tapstate --help` to inspect the commands in your installed version. In
the current preview, use `tapstate help <command>` or `tapstate <command> --help` for a
command's operands and options.

Text-mode results are written to standard output and usage or diagnostic messages
are written to standard error. With `-o json` or `-o yaml`, the structured
result, including validation diagnostics, is written to standard output.
Preserve both streams and the exit code when collecting evidence.

### CLI and server versions differ

The CLI and server are separate builds. When `connect` reaches a server on a
different version, the CLI reports `cli.version-mismatch` and keeps the
connection open. Run the following command in the same session to confirm both
values:

```text
version
```

Install the CLI version that matches the server, or connect to a server on the
CLI version. If their contracts differ, the server decides which operations it
accepts. Do not treat a successful connection as proof that every command is
compatible.

Text-mode coded CLI diagnostics include the CLI version and the server version
captured when the connection was made. Offline diagnostics say `server not
connected`; an older server that does not report a version appears as `server
not reported`. Structured JSON and YAML results keep their documented shape;
collect `tapstate version` separately when reporting one.

## Identify the failing layer

| Layer | Typical evidence | What it can establish |
|---|---|---|
| Documentation and resource shape | Page reference, YAML diff, schema diagnostic | Whether the resource follows the documented contract |
| Connector contract | Connector ID, mode, field names, preparation guide | Whether the requested role and configuration are declared |
| Deployment and connectivity | Runtime logs, network test, authentication response | Whether this deployment can reach and authenticate to the system |
| Data movement | Checkpoints, source and target samples, record counts | Whether Snapshot, CDC, transforms, and writes behave correctly |

Do not use evidence from one layer as proof of another. A valid resource file is the starting point; connectivity and data movement still need to be verified in the environment where the connection runs.

## Check the workspace first

Run the validation command supplied with your tapstate environment before investigating the external system:

```bash
tapstate validate --workdir tapstate-work
```

Review the filename, location, diagnostic code, message, and suggested fix. Correct one layer at a time, then validate again.

### Demo workspace already exists or cannot be written

`tapstate demo` protects existing files by default:

- `cli.demo-workspace-exists` means the target already contains a generated
  demo. Choose an empty work directory, or inspect the existing files before
  retrying with `--force`.
- `cli.workspace-not-writable` includes the failing `path` and filesystem
  `reason`. Correct the permission or choose a writable directory. The command
  restores replaced files and removes files it created, although empty
  directories from the failed attempt can remain.

### The `tap` alias is unavailable

The optional alias never replaces another command. `cli.alias-name-taken`
means the target path belongs to something else. Continue using `tapstate`, or
remove the conflicting command yourself before running `tapstate alias
install`. `cli.alias-install-dir-unknown` means the selected installation
directory has no `tapstate` entry; set `TAPSTATE_INSTALL_DIR` to the directory
used by the installer and retry.

### Unknown field or invalid value

- Confirm the connector ID and exact field spelling in its [Reference](/docs/connectors) section.
- Remove fields copied from an upstream UI or another connector version unless the tapstate contract exposes them.
- Check whether the field is conditional on another value, such as authentication method or storage type.

### Invalid mode

- Use only modes shown on the connector page.
- Do not add `cdc` because the underlying database supports a transaction log.
- A target-only connection does not need a source read mode.

### Missing or unresolved reference

- Confirm that pipeline references match resource IDs exactly.
- Keep every referenced resource in the selected work directory.
- Check for renamed files whose internal `id` did not change with the filename.

### Row-expression schema and type errors

These checks apply to `filter` expressions and computed `map` fields that read
`after.<field>` or `before.<field>`:

- `dsl.row-expression-needs-discovery` means at least one source that can reach
  the expression has no discovered schema. Apply the source connection by
  itself, run `discover-schema <source-id>`, then apply the pipeline or complete
  workspace again.
- `dsl.row-expression-type-unsupported` means the referenced column cannot be
  represented in CEL without losing information. Carry the column through
  unchanged, or compute from a compatible column instead.
- `dsl.row-expression-type-unknown` means the discovered schema has no resolved
  type for the referenced column. Remove that reference or use a column with a
  declared type.

These diagnostics restrict computation, not pass-through. A column that cannot
be computed losslessly can still flow through a `map` when no computed rule
reads it.

### Upsert source has no discovered primary key

`dsl.upsert-needs-key` is a server-side apply diagnostic. It means a selected
source table is being written with `upsert`, but its discovered schema has no
primary key. The diagnostic identifies the affected `source`, `table`, and
resource `path`.

Discover the source again and select a table with a primary key. A unique index,
a target-side key, or `tables[].pk` does not satisfy this runtime check. Use
`append` only when the delivery is insert-only and source updates and deletes do
not need keyed handling.

## Troubleshoot the Quickstart

The [Quickstart](/docs/overview/quickstart) assembles five MySQL orders
and six PostgreSQL shipments into MongoDB. Treat the run as successful only
when it prints this complete result:

```text
quickstart: 5 orders from MySQL, each carrying its shipments from PostgreSQL -- 6 of them, in one object per order
```

A healthy server or `order_pipeline running` line does not establish that the
assembled state is correct. Inspect the generated document when the success
line is missing.

### Docker is unavailable

```bash
docker info
docker compose version
```

Start Docker and confirm the Compose plugin is available. The Quickstart needs
to pull and run MySQL, PostgreSQL, MongoDB, and the tapstate server.

### A container is unhealthy or stopped

```bash
docker compose ps
docker compose logs --tail=200 mysql postgres mongo server
```

Fix port conflicts or local resource pressure before rerunning. Keep passwords and tokens out of shared log bundles.

### The assembled result does not appear

Check the source and target independently:

```bash
docker compose exec mysql mysql -uroot -psecret appdb \
  -e "SELECT COUNT(*) AS source_rows FROM orders;"

docker compose exec postgres psql -U postgres -d appdb \
  -c "SELECT COUNT(*) AS source_rows FROM shipments;"

docker compose exec mongo mongosh --quiet \
  'mongodb://mongo:27017/views?directConnection=true' \
  --eval 'printjson({orders: db.order_state.countDocuments({}), shipments: db.order_state.aggregate([{$unwind:"$shipments"},{$count:"count"}]).toArray()})'
```

If MySQL has five rows and MongoDB does not, enter the CLI REPL and collect pipeline evidence:

```bash
./tapstate -w work
```

```text
connect http://127.0.0.1:8080
login admin
status order_pipeline
metrics order_pipeline
logs order_pipeline
```

Enter the password stored in the local `.env` file. Do not paste it into a shell command or diagnostic bundle.

### A rerun reports an illegal lifecycle transition

The script preserves generated assets and may encounter a pipeline that is already running after a partial or completed attempt. Inspect `status` first. For a clean local reset, remain in `tapstate-demo` and run:

```bash
docker compose down -v
curl -fsSL https://install.tapstate.dev | sh
```

`down -v` permanently removes the Quickstart's local MySQL, PostgreSQL, and
MongoDB volumes. It does not remove files in the playground directory.

### The managed view store is unreachable

`actuation.view-store-unreachable` means the server cannot reach the managed
MongoDB store used for an inline `view`. Check the server's view-store
configuration and MongoDB health, then start the pipeline again. The
Quickstart's unauthenticated sample store is disposable and is not a production
security model.

### A connected command returns exit code 3

The command was invoked without a server connection, or the verb is reserved
but not implemented. Start an interactive session and run `connect` and `login`,
or seed a one-shot command with `-c` and `-u`. For automation, pass the password
through `TAPSTATE_PASSWORD` instead of `-p` so it is not exposed in shell history
or the process list.

### Connector registration is refused

`connector.not-official` means the server refused the artifact before
registration. In the current preview, the released registrar accepts the published MySQL,
PostgreSQL, and MongoDB preview connector artifacts. A catalog entry or a connector
JAR does not make another connector runnable. Confirm the artifact ID and use
`connectors -o json` after a successful registration; see [Register and test
connectors](/docs/guides/register-connectors) for the complete boundary.

## Check external-system preparation

If the resource shape is valid but a deployment cannot connect or discover objects:

1. Confirm DNS, port, routing, firewall, and allowlist rules from the runtime host.
2. Authenticate with the same account outside tapstate when a safe vendor tool is available.
3. Recheck source and target privileges separately.
4. Verify the database, schema, warehouse, tenant, topic, bucket, or API scope.
5. Follow the connector page's mode-specific preparation path.

For TLS and connection testing, use only the fields and workflow supported by the tapstate environment you operate. Do not copy certificate fields or test commands from another product.

## Check Snapshot or CDC behavior

### Table selection errors

Table selectors are resolved when the runtime builds the pipeline. Validate the
resource first, then run schema discovery for the source and apply the updated
resources before starting again.

| Diagnostic | What it means | What to do |
|---|---|---|
| `actuation.source-schema-not-discovered` | The source needs a discovered schema to expand an omitted `tables` field or a regex selector. | Run `discover-schema <source-id>`, then apply or start the pipeline again. |
| `actuation.source-table-not-discovered` | A named table is not in the source's current discovered schema. | Discover the source again and use the exact discovered table name. |
| `actuation.source-table-selection-empty` | The selectors resolve to no tables. This includes an empty list, a non-matching regex, or an omitted selector with no discovered tables. | Supply a literal name or a regex that matches at least one discovered table. |
| `actuation.source-table-ambiguous` | More than one pipeline source selects the same bare table name. | Where the pipeline names that table, replace the bare name with `source_id.table`. |
| `actuation.source-table-regex-invalid` | A table regex is not valid Java regular-expression syntax. | Correct the regex, keep it quoted when it contains YAML flow indicators, then apply the pipeline again. |
| `actuation.source-table-spec-unsupported` | A table object includes fields that the current preview capture path does not execute. | Use a literal or regex selector, or an object with `name` only. |

For an incomplete Snapshot:

- compare the selected object list with source discovery;
- check table-pattern and include/exclude rules;
- compare counts at a stable source boundary;
- inspect unsupported objects and data types in the connector limitations.

For CDC that stops or falls behind:

- check log, WAL, Oplog, snapshot, or broker retention;
- confirm that the saved recovery position still exists;
- verify replication or change-capture privileges;
- inspect long transactions and source-side cleanup jobs;
- test insert, update, delete, stop, and resume in staging.

## Check target correctness

- Confirm that updates and deletes have a stable key.
- Distinguish append behavior from key-based update behavior.
- Review automatic table creation and schema-change policy.
- Check target constraints, column types, partitioning, and conflict handling.
- Design downstream processing to tolerate duplicate delivery unless your deployment documents a stronger delivery guarantee.

## Interpret observations carefully

- `status` and `metrics` report observed state and may lag a lifecycle command briefly.
- `status --watch` and `logs --follow` continue until you press <kbd>Ctrl</kbd>+<kbd>C</kbd>.
- Logs are node-local in the preview and are not a durable audit history.
- `snapshot` can report that no snapshot is available. Confirm source and target records instead of treating that response alone as proof of success or failure.

## Collect a useful diagnostic bundle

Before escalating, collect:

- output from `tapstate version` and the deployment type;
- connector ID, role, and mode;
- redacted resource files;
- exact command and exit code;
- complete diagnostic or runtime error;
- relevant connector-page URL;
- external-system version and topology;
- timestamp and smallest reproducible dataset;
- expected and observed records.

Remove passwords, tokens, private keys, and customer data before sharing the bundle.
